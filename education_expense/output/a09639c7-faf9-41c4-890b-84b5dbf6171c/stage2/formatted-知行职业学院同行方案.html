执行摘要

本报告把《知行职业学院 · 业务需求发现报告》中的六条候选需求，转译为“同行怎么做、开源代码怎么落地、我们该借什么、不该借什么”的实施方案。检索与核实范围覆盖 GitHub 上的实习管理全流程系统、大模型结构化评审与评分框架，以及可观测与评测基础设施，所有仓库的 Stars、主语言与许可证均于 2026-10-23 通过 GitHub REST API 逐条核对。

核心判断有三条。第一，本项目真正的瓶颈不是“把文本整理成建议”，而是反馈缺少岗位任务与行为实例、评分口径未对齐、批次与导师映射不稳；同行案例中最值得借鉴的恰是“结构化组件 + 人工确认”这一层，而不是更强的生成能力。第二，GitHub 上不存在可直接复用的“实习反馈→课程改进”成熟开源项目，现存的实习管理系统只解决流程台账与成绩登记，AI 能力最贴近的是个人项目 trinethra，其成熟度与许可证不足以作为生产依赖。第三，可用性最稳的开源资产集中在旁路能力：文档解析、模型网关、评测与编排。

由此建议采用“轻改造 + 旁路增强”路线，把 AI 挂在既有流程旁边，而不是替换既有实习管理系统。最小试点与需求报告一致：机电专业、5 家企业、30 条历史反馈回放、8 周并行试点；预算 12 万元内优先投入数据映射与评测集建设，模型与框架全部走开源或按量付费，不自建 GPU 集群。

（一）实习管理类系统：解决台账，不解决能力缺口

wwqking/Internship-Management-System 是国内毕业设计级别的 Spring Boot + Vue 实习管理平台，三角色（管理员、教师、学生），功能覆盖实习信息、实习周报、实习成绩、论坛与公告。它的价值在于领域数据模型与中文业务语义：实习单位、岗位、周报、成绩、教师分工等实体关系可以直接对照，避免从零猜字段。短板同样明确：没有岗位任务层，没有行为实例，没有评分口径版本，仓库未声明许可证，最近推送为 2024 年 7 月，不能作为生产依赖。

NicolaKesla/ITS 是土耳其 Gebze Technical University 的实习跟踪系统，Node.js + Express + PostgreSQL + Prisma + React，含 JWT 鉴权与 pdf-parse 文档解析，覆盖从申请到评分、报告的完整生命周期。可借之处是工程结构与文档解析的位置（实习文件在入口即被解析，而不是后期补录），以及一份明确的安全加固清单。局限是角色仅到管理、委员会主席、委员会成员三级，没有企业导师视角，也没有任何 AI 组件。

M4CLEM/OIE-main 是菲律宾 PLMUN 的 OJT 管理系统，PHP + MySQL，最值得看的是可配置评分量规：协调员可按企业或批量定义评分标准与权重，导师与企业分别打分后由系统按量规计算最终成绩，并有“学生申请换企业需导师批准”的显式流程。它对本项目 R4（换岗交接）与 R2（口径校准）有直接参照意义——换岗在他们的系统里是一次带审批的显式事件，而不是后台静默改字段。

三者共同的缺口是：没有一个把“企业反馈文本”与“课程模块”连起来。这正是本项目要做的事，也是无法直接复用它们的原因。

（二）最接近的 AI 实现：trinethra 的四个设计决策

7upcharge/trinethra 是检索结果中与本项目最贴合的 AI 实现：粘贴督导反馈转写，约 60 秒产出结构化草稿，包含量规分（1–10）与理由、按信号与维度标注的证据摘录、KPI 映射、维度缺口分析，以及 3–5 条追问。它的四条设计决策可以直接搬到本项目。

第一，“草稿供复核”而非“结论”。界面顶部固定一条黄色横幅写明这是草稿，分数旁挂 high/medium/low 置信度徽标，模型被要求显式点名它检测到的偏差类型。这与 education-f24“未确认的结果不能覆盖原记录”高度一致，可作为交互层的直接参考。

第二，缺口检测用“逐项判定存在与否”而不是“你缺什么”。提示词把四个评估维度全部列出，要求模型对每个维度做存在性分类。这是把开放式问题转成结构化分类的经典技巧，直接对应本项目“行为实例是否缺失”的判定需求。

第三，结构化输出三级降级。先直解 JSON，失败则提取 JSON 块，再失败则从 Markdown 代码块提取，全失败带“只返回 JSON”的指令重试一次，并把所用解析方式写入元数据字段。解析方式本身成为置信度信号——这一点非常适合移植到“待补信息”队列的设计里。

第四，单次调用而非链路调用。作者在小模型上实测，五次串行调用需要 5 分钟以上，超出业务流程容忍度，因此选择单提示词加严格 schema。本项目在 5 家企业并行试点时同样受教师工时约束，这个权衡需要提前想清楚。

需要明确的是：trinethra 是单人项目，0 Stars，未声明许可证，仅支持本地 Ollama，无多租户、无审计日志、无权限分级。它只能作为参考实现与设计思路来源，不能作为依赖引入。

（三）方法论类：AutoSCORE 与 LaTA 回答“评分怎么做得可信”

AutoSCORE（AAAI/EAAI 2026，MIT）针对的正是“大模型端到端打分不可靠”的问题：准确率低、对提示词敏感、可解释性差、与量规不对齐。它的做法是拆成两个智能体——量规组件抽取智能体先从作答与任务上下文中识别与量规相关的证据，编码为结构化表示；评分智能体再基于该结构化表示给出分数。在 ASAP 四个数据集上，用 GPT-4o、LLaMA-3.1-8B/70B 评测，多智能体方案在 QWK、相关性、MAE、RMSE 上一致优于单智能体基线，且在复杂多维量规上收益最明显，在小模型上相对提升最大。

对本项目的直接启发：不要让模型直接输出“这条建议可不可执行”，而是先抽“岗位任务—行为实例—能力项”三元组作为结构化中间层，再由规则或人工判定“可执行”。这一拆分同时解决两个问题——可解释性（每条结论都能回溯到抽取到的组件）与小模型可用性（试点预算 12 万元，不可能全程用最强模型）。

LaTA 是 Gradescope 作业批改流水线，四段式：Ingest（读取提交与元数据，迟到判定取两个文件的较晚时间）→ Segment（按模式或小模型切分题目）→ Grade（推理模型对照参考解与量规逐题评分，返回结构化 JSON：每个量规项得分、给教师的内部审计备注、给学生的苏格拉底式提示）→ Report（渲染为反馈报告）。两个细节值得抄：评分结果在使用前要与量规做一次校验，以及审计备注与学生可见反馈是两份不同的产物。后者正好对应本项目“教师看到的原文与依据”和“学生看到的改进建议”必须分离的要求（education-f13、education-f33）。

（四）基础设施类：可用性最高的一层

这一层的价值不在于“像不像同行”，而在于决定试点能否在 8 周内跑起来。

Docling（MIT，69k Stars）负责把企业发来的 Word、PDF 问卷与评价表批量转成结构化文本，MarkItDown（MIT，191k Stars）作为轻量兜底。本项目现场大量反馈是微信截图、Excel、邮件附件（education-f06），解析层的稳定性直接决定“反馈完整率”能不能从 54% 走到 85%，这是最容易被低估的一环。

LiteLLM（61k Stars）作为统一模型网关，把模型调用抽象成同一接口，好处是成本可观测、可切换、可降级：某家模型不可用时自动回退，符合 education-f30“接口失败时继续人工流程”的兜底要求。

DeepEval（Apache-2.0，19k Stars）与 Promptfoo（MIT，26k Stars）负责把“建议可执行”变成可回归的评测集。这一点是很多同类项目失败的地方：改了提示词，没人知道变好还是变坏。建议把 30 条历史反馈的回放结果固化为评测集，每次规则或提示词变更都跑一次，把“至少 24 条可执行”作为发布门禁。

Dify（159k Stars）与 open_deep_research（MIT，12.7k Stars）提供编排层参照。后者的“规划 → 并行子智能体 → 反思 → 压缩 → 合成”结构，以及“子智能体各自隔离上下文”的做法，适合本项目按企业或按专业批量处理反馈时避免上下文串味。

四、推荐架构

推荐架构的目标是让每一个环节都能单独替换、单独验证：数据层不动原记录，解析层不猜缺失值，模型层只出草稿，确认层由人签核。

观测与评测层成本、质量、回归LiteLLM、DeepEval / Promptfoo不用模型置信度代替业务风险判断

（二）关键设计决策

决策一：把“可执行”定义成可判定的三元组。一条建议被视为可执行，当且仅当它能同时给出：对应的课程或课程模块、对应的岗位任务、以及明确的改进负责人。这个定义与验收口径（education-f15）逐字对齐，也让“至少 24 条”变成可逐条判定的清单，而不是主观印象。

决策二：模型只做抽取与起草，不做判定与打分。模型输出“行为实例候选 + 能力项候选 + 建议草稿”，是否成立由专业组签核。这与 education-f18“AI 可整理观察事实与建议，最终评价由导师确认”完全一致，也规避了“模型决定学生成绩”的红线。

决策三：所有结果必须携带原记录与版本。每条建议输出需带业务编号、资料版本、事件时间、来源，缺一不可（education-f28）。这与 LaTA 的“审计备注”思路一致：面向教师的记录必须能重建当次处理，面向学生的内容只保留改进提示。

决策四：兜底优先于准确率。触发条件包括学生换岗、评价无行为实例、评分口径不一致、依据缺失、关键系统不可用。命中即停止自动建议，标明原因、接手人与人工确认时间（education-f32）。宁可少给建议，也不给无法追溯的建议。

（三）双周轻量反馈的最小闭环

针对 R3，建议把企业导师的长问卷拆成双周一次的“三个具体任务例子”模板，只问三件事：这两周学生做了哪个岗位任务、哪一次做得明显好或明显差（要有具体场景）、下两周希望他改进什么。理由是 education-f16 已明确“长问卷会拖到学期结束才填”。教师端的整理工时从每月 10 小时压缩到审核与补录，解析与归类交给解析层和组件抽取层。

  这里必须守住一条统计纪律：完整率的分子分母由业务负责人固定，不能用消息发送量代替实际完成量（education-f34）。双周模板发出去不等于收到，收到不等于有行为实例。

七、结论与建议

第一，本项目不宜以“替换实习管理系统”为路径。路线 A 在 8 周与 12 万元两个约束下都不可行，且与“不能直接关掉现有人工流程”直接冲突。

第二，GitHub 生态在本细分领域没有成熟可用的直接方案，这本身是重要信息：说明该问题在行业内普遍存在但尚未被产品化，自建组件抽取与可执行判定有实际价值，但也意味着没有现成的质量基线可以对齐，必须自建评测集。

第三，建议把 70% 的实施精力放在“数据映射 + 行为实例抽取 + 可执行判定口径”三件事上，把模型能力、编排、界面都当作可替换部件。AutoSCORE 的组件抽取思路、trinethra 的草稿复核交互、LaTA 的审计与学生反馈分离、OIE-main 的量规配置与换岗审批，是本轮最值得借鉴的四个具体做法。

第四，试点成功的判据不是“AI 生成了多少建议”，而是两条硬指标：专业组审阅 30 条中至少 24 条能对应课程、任务与改进负责人；反馈完整率从 54% 到 85%，且分母口径由业务负责人固定。未达标不扩面。
