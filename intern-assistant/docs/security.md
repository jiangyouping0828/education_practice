# 安全设计（Security）

## 1. 威胁模型与对策总览

| 威胁 | 攻击面 | 对策 | 防线层级 |
|------|--------|------|----------|
| AI 编造制度条款 | LLM 生成 | 检索不到即拒答 + 回答必附文档来源 | 提示词纪律（软） |
| 提示词注入（"忽略之前的指令"） | 用户输入 | 注入特征检测留痕 + 提示词纪律 + **提交动作不在模型手里** | 检测（发现）+ 架构（根治） |
| 越权提交 / 伪造申请 | 工具调用 | 票据硬闸门：一次性 / 10 分钟 / 内容哈希绑定 | 服务端闸门（硬） |
| 跨学生偷看数据 | 会话接口 | 登录身份 + 归属校验，越权 403 | 服务端（硬） |
| 管理员滥用查看 | 后台记录页 | admin_access_log 全量留痕 + 页面明示审计 | 制度 + 留痕 |
| 敏感信息落日志 | 日志/审计表 | 手机号/身份证正则脱敏（utils.security），工具结果只存 200 字摘要 | 数据最小化 |
| API Key 泄漏 | 代码仓库 | .gitignore + pre-commit detect-private-key + 错误信息不回显 key | 流程 |
| 配额滥用 / 刷量 | chat 接口 | 滑动窗口限流 10 次/分钟、100 次/天，超限 429 不计费 | 服务端（硬） |

## 2. 票据硬闸门（核心机制）

```
学生提交意向 → AI 调 validate_apply_material（服务端校验材料 → 签发票据）
            → AI 调 create_intern_draft（服务端强制中断，展示草稿）
            → 学生点【确认】→ POST /api/draft/{id}/confirm
                             → verify_ticket：存在性/归属/过期/复用/内容哈希
                             → 全部通过才核销票据并置 submitted
```

关键性质：

- **唯一核销点**：只有确认接口消费票据，任何其他路径（包括模型输出）都无法提交；
- **内容绑定**：票据签发时记录 payload 的 SHA-256，确认时逐字比对，改一个字即 PAYLOAD_MISMATCH；
- **一次性 + 10 分钟**：防重放与过期幽灵提交，拒绝码 TICKET_REUSED / TICKET_EXPIRED；
- **9 条对抗单测**持续守护（tests/test_core.py）。

## 3. 提示词注入防护

用户说"忽略之前的指令"时系统的实际行为链：

1. `utils.security.detect_injection` 命中"指令覆盖"特征 → 控制台留痕（脱敏输出）；
2. 系统提示词纪律要求只依据工具返回的制度片段回答——注入不改变可用信息源；
3. **结构性防御**：即便模型完全被"策反"，它能做的只有调用工具——而提交类动作必须持有服务端签发且校验过的票据，注入无法凭空获得；
4. 上传文档内的间接注入同理：文档内容只会进入检索片段，不进入任何执行路径。

## 4. 数据隔离

- 学生与管理员令牌分表（student_tokens / admin_tokens），互不通用；
- 会话、申请单全部绑定 user_id；读历史 / 续问 / 确认 / 取消四个接口逐一校验归属；
- 管理员可查看全部记录（督导需要），但每次查看写入 admin_access_log，详情页显示累计查看次数；
- 7 条隔离测试（tests/test_isolation.py）在 CI 中持续验证。

## 5. 已知限制（如实声明）

- 限流器与令牌为进程内存态，重启清零；多实例部署需 Redis 后端；
- 管理后台暂无改密页，改密需 DBA 操作（见 deployment.md）；
- 注入检测为正则特征，存在绕过可能——因此最终防线是闸门架构而非正则本身；
- SQLite 未加密，宿主机磁盘访问控制依赖部署环境（全托管机房/内网）。
